# Project 09 — SSH & Remote Administration

## Overview

This project focuses on secure remote administration of a Linux server using OpenSSH.

The project explores the SSH client-server architecture, public-key authentication, client and server configuration, host identity verification, basic SSH hardening, secure file transfers, remote command execution, and systematic troubleshooting.

The practical work was performed between a macOS client and an Ubuntu Server virtual machine, progressing from password-based access to a hardened public-key authentication setup.

---

## Learning Objectives

- Understand the SSH client-server architecture.
- Configure public-key authentication for remote access.
- Understand the roles of private keys, public keys, `authorized_keys`, and `ssh-agent`.
- Distinguish client-side SSH configuration from server-side `sshd` configuration.
- Inspect and validate the effective OpenSSH server configuration.
- Apply basic SSH hardening safely.
- Understand server host keys and `known_hosts`.
- Transfer files securely using SCP and SFTP.
- Execute commands remotely and interpret their exit status.
- Troubleshoot SSH connectivity and authentication problems using client and server information.

---

## Concepts Covered

### SSH Client and Server Architecture

SSH communication involves two primary components:

- `ssh` — the client used to initiate remote connections.
- `sshd` — the server daemon responsible for accepting SSH connections.

The client configuration was managed through:

```text
~/.ssh/config
```

using a host alias that defined the server address, remote user, and identity file.

Server-side configuration was inspected through:

```text
/etc/ssh/sshd_config
/etc/ssh/sshd_config.d/
```

This established a clear distinction between configuring how a client connects and defining how the server accepts connections.

### Public-Key Authentication

An ED25519 key pair was generated on the macOS client.

The private key remained on the client, while the corresponding public key was installed in:

```text
~/.ssh/authorized_keys
```

on the Ubuntu server.

Verbose SSH output was used to confirm that authentication successfully changed from password-based authentication to public-key authentication.

`ssh-agent` was also configured to hold the unlocked client identity in memory, allowing repeated SSH connections without repeatedly entering the private-key passphrase.

### SSH Server Configuration

The OpenSSH server configuration was inspected using both configuration files and the effective configuration reported by:

```bash
sshd -T
```

The project demonstrated that the contents of configuration files do not necessarily represent the final configuration used by the daemon.

Configuration fragments under `sshd_config.d` were also investigated, including the interaction between locally defined settings and configuration generated by `cloud-init`.

Before applying configuration changes, syntax was validated using:

```bash
sshd -t
```

This validation detected configuration errors before they could affect the running SSH service.

### SSH Hardening

A dedicated OpenSSH configuration fragment was introduced to enforce the following policy:

```text
PasswordAuthentication no
PermitRootLogin no
```

The resulting effective configuration was verified as:

```text
pubkeyauthentication yes
passwordauthentication no
permitrootlogin no
```

The SSH service was reloaded only after configuration validation, while an existing SSH session remained open as a recovery path.

A second connection was then used to verify that public-key authentication continued to work while password authentication was rejected.

### Server Identity and Host Keys

The project distinguished user authentication keys from SSH server host keys.

Server host keys identify the SSH server to connecting clients, while user keys identify authorized users to the server.

The ED25519 host key fingerprint was inspected directly on the server and compared with the fingerprint presented to the macOS SSH client.

The client's:

```text
~/.ssh/known_hosts
```

file was inspected to understand how previously observed server identities are stored and verified.

The following commands were also explored:

```bash
ssh-keygen -F <host>
ssh-keygen -R <host>
```

This demonstrated how SSH can detect unexpected server identity changes and why host-key warnings should be investigated rather than bypassed automatically.

### Secure File Transfer

SCP was used for direct encrypted file transfers in both directions:

```text
macOS → Ubuntu Server
Ubuntu Server → macOS
```

SFTP was then used to explore interactive file transfer, including the distinction between local and remote working directories.

The practical work included:

```text
get
put
pwd
lpwd
ls
lls
```

Both tools reused the existing SSH authentication and host verification infrastructure.

### Remote Command Execution

SSH was used to execute commands remotely without opening an interactive shell.

Examples included retrieving:

- the remote hostname,
- the remote user,
- the working directory,
- server uptime.

Multiple remote commands were also executed as a single operation.

The project verified that the exit status of a remote command is propagated back through SSH, allowing remote operations to be integrated into shell scripts and automation workflows.

### SSH Troubleshooting

SSH troubleshooting was approached as a layered process involving:

1. Host and network reachability.
2. Listening ports and services.
3. SSH protocol negotiation.
4. Server identity verification.
5. User authentication.
6. Session establishment.
7. Server-side logging.

Listening SSH sockets were inspected using `ss`, confirming that SSH was listening on TCP port 22.

A connection attempt to an unused port demonstrated the difference between a connectivity/service failure:

```text
Connection refused
```

and an authentication failure:

```text
Permission denied (publickey)
```

Verbose client output with `ssh -v` was used alongside server-side logs from:

```bash
journalctl -u ssh
```

to correlate both perspectives of an SSH connection.

## Practical Exploration

The project began by inspecting an existing SSH connection that used a host alias from the macOS SSH client configuration.

Verbose SSH output revealed that the configured identity file did not initially exist and that the connection was silently falling back to password authentication.

A new ED25519 client key pair was generated and the public key was installed on the Ubuntu server. Public-key authentication was then verified through verbose SSH output.

`ssh-agent` was configured to manage the unlocked client identity and simplify repeated authenticated connections.

The OpenSSH server configuration was then investigated. The main configuration file, configuration fragments, OpenSSH defaults, and the effective configuration were compared.

A dedicated hardening configuration was introduced to disable SSH password authentication and direct root login. Configuration syntax and effective values were validated before reloading the SSH service, and new connections were tested before the original administrative session was closed.

Server host keys and the client's `known_hosts` database were inspected to understand server identity verification and host-key fingerprints.

SCP and SFTP were used to transfer test files between the macOS client and Ubuntu server.

Remote commands were executed directly through SSH, including successful and intentionally invalid commands, demonstrating how remote exit codes are returned to the local shell.

Finally, SSH troubleshooting was explored through listening socket inspection, controlled connection failures, verbose client diagnostics, and server-side journal analysis.

---

## Key Takeaways

- SSH separates server identity verification from user authentication.
- Private keys must remain on the client; only public keys are installed on remote servers.
- `authorized_keys` defines which public identities may authenticate as a remote user.
- `ssh-agent` simplifies repeated use of passphrase-protected private keys.
- Client configuration and server configuration serve fundamentally different purposes.
- Written configuration should not be assumed to equal effective configuration.
- `sshd -t` should be used to validate SSH configuration before applying changes.
- SSH configuration changes should be applied while maintaining an existing administrative session whenever possible.
- Disabling password authentication significantly changes the remote authentication policy without removing the Linux user's password.
- Direct root SSH access can be disabled independently from local privilege escalation through `sudo`.
- Host-key warnings should be investigated rather than automatically removed from `known_hosts`.
- SCP and SFTP reuse SSH's authentication, encryption, and host verification mechanisms.
- SSH can execute remote commands non-interactively and propagate their exit status.
- Effective troubleshooting requires identifying whether a failure occurs at the connectivity, service, identity, authentication, or session layer.
